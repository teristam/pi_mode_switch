# Model selector API compatibility fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the `/mode` editor open Pi's built-in model selector correctly with the current `0.84.4+` constructor API.

**Architecture:** Keep the existing adapter from the extension-facing `ModelRegistry` to the selector's runtime-shaped interface. Extract the model submenu construction into one small helper so the exact constructor argument order is directly regression-tested; the settings manager is removed because it is not part of the current selector API.

**Tech Stack:** TypeScript, Node test runner through `tsx`, `@earendil-works/pi-coding-agent`, npm lockfile.

### Task 3: Implement the current constructor integration

- [ ] **Step 1: Add the smallest model-selector factory**

Remove `SettingsManager` from the value imports. Add this helper directly after `modelReference`:

```ts
export function createModeModelSelector(
  tui: TUI,
  currentValue: string,
  ctx: Pick<ExtensionContext, "modelRegistry" | "scopedModels">,
  done: (value?: string) => void,
): ModelSelectorComponent {
  const separator = currentValue.indexOf("/");
  const currentModel = separator > 0
    ? ctx.modelRegistry.find(currentValue.slice(0, separator), currentValue.slice(separator + 1))
    : undefined;

  return new ModelSelectorComponent(
    tui,
    currentModel,
    createModelSelectorRuntime(ctx.modelRegistry),
    ctx.scopedModels,
    (model) => done(modelReference(model)),
    () => done(),
  );
}
```

This places the adapted runtime third, matching `0.84.4+`:

```ts
(tui, currentModel, modelRuntime, scopedModels, onSelect, onCancel, ...)
```
